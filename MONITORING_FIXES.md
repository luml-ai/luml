# Мониторинг: состояние работ

Заметка по итогам отладки live-мониторинга на локальном стенде (демо-модель `lisa_router`,
25 фич: 15 числовых + 10 категориальных; плюс табличные модели iris и insurance).

Что здесь: сверху — что осталось сделать, ниже — что уже сделано и где именно были
поломки. Всё сделанное лежит в восьми коммитах ветки (`54a099c9 … 7af329c3`).

## Что надо сделать

### 1. Realized performance (крупное, на несколько дней)

Единственный большой раздел спеки, которого нет совсем: качество модели по факту, когда
приходят настоящие ответы. Спека описывает его в разделах Performance tab, Alerts
(пятая группа «realized performance, when targets are available») и Calculation Strategy
(«recompute affected performance windows after delayed targets arrive»).

Что нужно сделать:

- **Приём таргетов**: эндпоинт на сателлите, куда клиент присылает фактический ответ по
  `request_id` (спека: «target submission directly to the Satellite Monitoring API»).
  Авторизация — тем же inference-ключом, что и предсказания.
- **Хранение и джойн**: таргет приходит с задержкой (часы, дни), поэтому его нужно класть
  отдельно и джойнить с событием инференса по id, а не ждать в момент запроса.
- **Метрики по типу задачи**: регрессия — MAE, RMSE, R², распределение остатков,
  predicted vs actual; бинарная классификация — accuracy, precision, recall, F1, ROC-AUC,
  confusion matrix; многоклассовая — accuracy, macro/micro F1, log loss, confusion matrix.
  Плюс **target coverage**: какая доля предсказаний вообще получила ответ.
- **Пересчёт окон**: опоздавший таргет меняет уже посчитанное окно, воркер должен уметь
  его пересчитать (механика догона окон уже есть, см. «Догон пропущенных окон»).
- **Вкладка Performance** с честным пустым состоянием: пока таргетов нет, вкладка должна
  говорить, что остальные разделы работают и без них.
- **Пятая группа алертов** — по деградации качества.

Решения, принятые заранее (20.08): реального потребителя таргетов пока нет, поэтому
делаем **API + демо-генератор** в `dfs_test` рядом с генераторами трафика, чтобы прогнать
путь целиком; таргеты шлёт клиентский бэкенд напрямую в сателлит, как в спеке, а не через
платформу.

### 2. Prediction drift (средний)

Есть в дизайне (`y_pred` median с полосой p05–p95), данные воркер уже считает
(`output_drift.trend`), но в Query API нет секции output drift и во вкладках дашборда нет
соответствующего блока. Метрика и алерты по output drift при этом работают — не хватает
только представления.

### 3. Передеплоить старые модели

Артефакты, собранные до правок SDK, не содержат `reference_projection`, поэтому облако
reference на PCA-скаттере у них пустое. Проверено 19.08 — пустые: `019ffc8e` (ref 3),
`019ffc8f` (ref 4, вообще без окон), `01a0143d-4711` (tab c), `01a0143d-875b` (tab reg).
Новые демо-деплои в порядке: 400 / 150 / 400 точек и оба эллипса.

### 4. Прибраться на демо-стенде

Три деплоя называются `01a014f8 monitored` / `01a01502 monitored` (PATCH имени отвечал
500), и висит failed-деплой `01a014fd-1e82-7018-aaeb-f3485744b8bc` (insurance, не
поднялся).

### 5. Мелочи

- **dev-группа `wasm/packages/dfs_webworker`**: тесты пакета не запускаются локально —
  `__init__.py` тянет forecasting → `statsmodels`, дальше `promptopt` → `httpx` → `optuna`,
  а в dev-зависимостях их нет. Профиль проверяли, загружая модули из wheel по файлам.
- **`environment` в шапке дашборда** остаётся пустым: такого поля нет в записи деплоя на
  платформе (есть только `orbit_id` без имени), UI просто пропускает его. Чтобы заполнить,
  платформа должна отдавать имя орбиты в `/satellites/v1/deployments`.

### Инфраструктура

- [x] **Ретеншен.** Не чистилось вообще ничего. Теперь у трёх таблиц TTL из настроек, по 30
      дней. Срок выбран по самому длинному окну дашборда: если события истекают раньше,
      вкладка Traces на 30d молча покажет неполную картину, что читается как «трафика не
      было». Метрикам сырые события нужны намного меньше — окно считается сразу после
      закрытия, догон ограничен часом. Совсем без TTL оставлять нельзя: это единственная
      таблица, которая быстро растёт и хранит входы модели. TTL проставляется при каждом
      старте, в том числе на существующие таблицы и на таблицу трейсов коллектора; сбой
      `ALTER` только пишет предупреждение.
- [x] **Догон пропущенных окон.** Воркер считал ровно предыдущее закрытое окно: полчаса
      простоя — и эти окна не досчитывались никогда. Теперь он спрашивает у хранилища,
      докуда досчитано (`max(window_end)` — ответ переживает рестарт), и добирает
      пропущенное от старых к новым, не больше `MONITORING_BACKFILL_MAX_WINDOWS` (12) за
      тик. Свежий деплой начинает с настоящего момента, а не переигрывает историю базы.
      Проверено: агент остановлен на 11 минут, после старта досчитал 09:40, 09:45, 09:50.
- [x] **Self-health воркера.** Упавшая метрика ловится и пропускается, чтобы не утащить
      остальные, — для инференса правильно, для доверия нет: пустая вкладка выглядит
      одинаково и когда трафик чистый, и когда метрика час подряд падает. Теперь есть
      счётчики (`agent/monitoring/health.py`) и `GET /monitoring/api/worker`, а на Overview —
      полоска «Monitoring worker · last run … · N windows · 180s behind the window it closed».
- [x] **История падений метрик.** Счётчики в памяти обнуляются рестартом, поэтому переходы
      пишутся в `monitoring_worker_failures`: строка, когда метрика начала падать, и строка,
      когда вернулась. Только переходы — метрика, сломанная на сутки, стоит две строки, а не
      по одной на тик, и число строк читается как число инцидентов. Дашборд собирает из них
      отрезки «была сломана с… по…», в том числе уже закончившиеся. Колонки называются
      `message` и `happened_at`: `error` и `at` — зарезервированные слова в GreptimeDB.
- [x] **Два падавших теста** `test_monitoring_flag.py` починены: мокали литеральный
      `https://api.luml.ai`, а агент ходит по `config.PLATFORM_URL`.

## Приложение: multivariate drift (PCA)

### Что это за метрика

Univariate-дрейф смотрит на каждую фичу отдельно и не замечает, когда рвутся связи между
ними: `prompt_tokens` и `context_tokens` могут остаться в своих привычных диапазонах, но
перестать расти вместе — по каждой фиче «нормально», а трафик уже другой.

Multivariate ловит именно это. На обучении по числовым фичам обучается PCA и запоминает оси
реальной изменчивости данных, а вместе с ними — облако обучающих скоров: вектор средних и
ковариацию (`pca_profile.reference_distribution`). В проде каждая живая строка
стандартизуется, проецируется на те же компоненты и измеряется **расстоянием Махаланобиса**
до этого облака. Оно учитывает и разброс, и корреляцию компонент, поэтому строка, обычная по
каждой фиче в отдельности, всё равно выделяется, если такое сочетание значений на обучении
не встречалось.

Под обучающим распределением квадрат расстояния подчиняется χ² с одной степенью свободы на
компоненту, поэтому линия выброса — её 99-й перцентиль: на здоровом окне за неё уходит около
1% строк. Метрика считает реальную долю (`outlier_rate`) и поднимает warning при 5%,
critical при 10%.

### Что было и что стало

Метрика считалась, но панель была пустой — воркер не писал ничего из того, что она рисует
(`shift_value`, `explained_variance`, `projection` приходили пустыми). Плюс два более ранних
блокера: `_numerical_rows` ждал скаляры вместо батчей, а в профиле не было baseline ошибки
реконструкции при PCA полного ранга (при таком базисе строки восстанавливаются точно,
baseline вырождается в ноль, и порог сработал бы на любом шуме).

Метрика переведена на махаланобис по `reference_distribution`, как в спеке. Обратная
ковариация считается методом Гаусса–Жордана с частичным выбором ведущего элемента (numpy и
SciPy в агенте нет), квантиль χ² — приближением Уилсона–Хилферти. Компонента с нулевой
дисперсией означает, что мерить расстояние не в чем: метрика пропускает окно, а не объявляет
выбросом каждую строку. В окно пишутся `mean_distance`, `p95_distance`, `outlier_rate`,
`outlier_threshold` и всё, что рисует панель.

Побочный эффект: `reference_distribution` есть и в **старых** профилях (его писал ещё
первоначальный SDK), поэтому метрика заработала и на моделях из Express Tasks — без
пересборки wheel.

Проверено на живых данных (`019ffc8e`, 25 фич, 11 компонент PCA, окно из 295 строк с
дрейфующим трафиком): `severity critical | mean_distance 7.62 | p95 6.56 | порог выброса
4.98 | outlier_rate 0.19` при ожидании ~0.01 на здоровом окне.
